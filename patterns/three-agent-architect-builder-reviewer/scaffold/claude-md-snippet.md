## Delivery pipeline — three-agent Architect / Builder / Reviewer

**Operating mode: `supervised`** <!-- switch to `autonomous` once the pattern holds on this repo -->
**Tracker: `gh`** <!-- gh (GitHub) or glab (GitLab); set by adopt.mjs from the origin remote. Commands and workflows read the platform from THIS line — correct it if adopt guessed wrong. -->
**Default branch: `main`** <!-- detected by adopt.mjs from git; the branch every ticket merges into. -->
**Test command: `(unset)`** <!-- REQUIRED (catalog issue #190). The exact command the Builder and the Reviewer run — e.g. `npm test`, `pytest -q`, `go test ./...`. adopt.mjs fills it from package.json `scripts.test` where it can and writes `(unset)` where it cannot. `(unset)` is a value, not an absence: a missing line reads like an older install, a present `(unset)` reads like a question nobody answered. -->

- `supervised` — issue **creation** is authorized by the `/start-milestone` sign-off itself. On each CLEAR the runner **opens a PR/MR** (carrying the plan, `Closes #N`, and the Reviewer's CLEAR verdict as a comment) and stops for the human to review + merge — re-run `/start-milestone` to continue (closed issues are skipped). Use for a fresh adoption.
- `autonomous` (target) — humans decide at exactly two gates **per phase**: Gate 1, sign-off of PRD → sub-PRDs → tickets before the pipeline starts; Gate 2, a smoke test of the delivered work. A project that adds a phase after Gate 2 runs the same two gates again over the new PRD — Gate 2 is per delivered phase, not once per project lifetime. Between them the pipeline self-drives: merge on CLEAR, `/verify-delivery` repairs gaps (including closing the issue) automatically. A human is pulled in only on the exception path — 2 bounce cycles without convergence, a failed build, or an unrepairable verify-delivery item.

Every non-trivial ticket flows through three stages; no agent judges its own work.

- **`/breakdown-prd [prd-path] [notes]`** — pre-Gate-1: the Architect decomposes a PRD (default `docs/PRD.md`) into a breakdown plan + sub-PRDs + template-compliant tickets (disjoint file-scopes, dependency DAG), then writes the execution-plan view to `docs/prd/dag.html` (`dag-report.mjs` — one whole-PRD flowchart colored by module, plus the **recommended `concurrency`** for `/start-all`) and stops for human review. A module flagged **fully serial** there is a file-scope decomposition problem to fix before Gate 1, not a scheduling detail.
- **Adding work after Gate 2 — phased PRDs.** A project does not end at Gate 2. The next phase gets its own PRD **document** (`docs/PRD-02-<name>.md`, passed as the `prd-path`), decomposed into the **same `docs/prd/` tree**. The document splits by phase; the ticket tree never does — `dag-scan.mjs`, `dag-report.mjs` and `/start-all` each take one root, and a cross-phase `blocked_by` only resolves inside one graph. In append mode `prd-phase.mjs context` hands the Architect the next module prefix, the ticket ids already in use, and the existing-file list; **`prd-phase.mjs check` then enforces, against git, that no pre-existing file under `docs/prd/` was modified or deleted** — only additions. Delivered tickets are the record of what was built. A new ticket may be `blocked_by` a delivered one; that edge is honored and drawn, and does not re-run it. Then just `/start-all` again: phase 1's issues are closed, so only the new tickets run.
- **`/plan-ticket <ticket>`** — Architect (`claude-opus-5` @ `high`) reads the ticket + codebase → implementation plan at `docs/plans/<ticket-id>.md`. Writes no production code.
- **`/build-ticket <ticket>`** — Builder (`claude-opus-5` @ `medium`) implements the plan, runs tests until green, records deviations. Never merges or self-clears.
- **`/review-ticket <ticket>`** — Reviewer (`claude-sonnet-5` @ `high`) in a **fresh context**, deliberately a different model from the Builder — different, not stronger: the point is that two models fail differently, and since 2026-07-29 the Reviewer is the lower tier (upstream issue #111). Focus: edge cases, concurrency, security-sensitive paths. Verdict **CLEAR** or **BOUNCE**; merge requires CLEAR.
- **`/verify-delivery <ticket>`** — post-merge Definition-of-Done check: plan on disk · tests green · **CLEAR verdict attached to the PR/MR as a comment** · MR/PR merged into the default branch · **tracker issue closed** · writeback done. Run after **every** merge; tracker auto-close side effects are never trusted blindly.
- **`/start-milestone <module> [mode]`** — the Gate 1 start signal: verify sub-PRD + tickets, publish tickets as tracker issues (deterministic idempotent script — agents never hand-create issues), then run every ticket through the deterministic `run-milestone` workflow (stage order, bounce cap, merge policy enforced in code).
- **`/start-all [mode] [concurrency]`** — Gate 1 for the **whole PRD**: publish every module's tickets, then schedule them all from **one flat DAG** (`dag-scan.mjs`, deterministic — cycles and dangling refs fail loudly). It is *not* a sequence of `/start-milestone` runs: only `blocked_by` gates, so independent modules overlap. A failed ticket cascades to its dependents; independent branches continue in `autonomous`; anything short of a CLEAR stops the run in `supervised`. Re-run to resume — tickets with closed issues are filtered out, **and the run reports what it dropped**: a filter that removes work silently is indistinguishable from work that ran. A ticket edited *after* it was delivered comes back as `drift` — a human decides whether to re-run it; the scheduler never does it silently (issue #112). Optional `concurrency` (default 1 = sequential): `>1` runs independent tickets as **parallel lanes** (autonomous only), each in an isolated git worktree with deliver serialized; take the value from `dag.html` rather than guessing, and note it multiplies concurrent token spend. **The DAG stays live**: every few settled tickets the run re-reads `docs/prd`, so a ticket added while it is running gets published, scheduled, executed, and re-rendered. Things it cannot honor — a dependency added to an already-started ticket, a mid-run cycle, a failed reload — come back in `escalations`; relay them, never summarize them away.
- **`/publish-tickets <module> [--all]`** — publish only: create the tracker issues (and Asana subtasks, if connected) and **stop**. No planning, no building. For getting the board populated before work starts. Authorizes issue creation; it is *not* Gate 1 sign-off to build.
- **Integration branch: `(none)`** — set this to a branch name (convention: `ai-staging`) to enable the protected-default-branch fallback. In **autonomous** mode only, a merge the default branch refuses **because it is protected** lands there instead of stalling the run; an unmet gate (failing pipeline, missing approval) still escalates, and the classifier fails closed on anything it does not recognise. Work delivered there closes its issue — so re-runs do not rebuild it — but **does not pass the Definition of Done**: `dodPassed` gates on the default branch, the outcome is reported as `delivered-to-integration`, and the run must say plainly those tickets are not on the default branch. At the end of a run one handoff MR is **opened and never merged**; landing that work is a human decision.
- **`/nightly-issues [max]`** — unattended sweep (OS-scheduled, `claude -p`): triage open issues → auto-fix fixable ones through the pipeline → per-issue comments + labels + a `Nightly report <date>` issue for the morning read. Invalid issues are labeled `triage:invalid`, never auto-closed. Setup: scaffold INSTALL.md § Nightly sweep.

Orchestrator discipline (hard rules for the main session):

- The main session **orchestrates only**: it invokes the stage commands and relays artifacts (ticket path, plan path, diff ref). It never plans, implements, or reviews a ticket inline — that work belongs to the stage subagents, whatever the size of the change.
- If a stage subagent fails or is unavailable, report the failure and stop. **Never absorb its role.**
- This is **mechanically enforced**: a PreToolUse guard (`.claude/hooks/guard-main-session-writes.mjs`) denies Edit/Write in the main session; subagent calls pass. For a human-approved out-of-pipeline edit, create `.claude/allow-main-writes` (git-ignored) and delete it afterwards.
- Known guard boundary: Bash is not covered. Bash in the main session is for orchestration only (git, tracker CLI, running commands) — never for writing files (`echo >`, `git apply`, heredocs). The guard stops reflexive edits, not determined bypasses; this rule covers the rest.
- A ticket is done only when `/verify-delivery` passes all items — "the MR is merged" is not done (known failure: MRs merged with issues left open, observed 2026-07-17).

Rules:

- The Reviewer never runs in the Builder's session and never edits code; it receives only the ticket, the plan, and the diff ref — never transcripts.
- Maximum 2 bounce cycles, then escalate to a human.
- Trivial/mechanical changes may skip the pipeline only with an explicit human OK.
- **The ticket is the executable source of truth (WHAT)** — authored by the Architect (`/breakdown-prd`), it IS the spec. `docs/plans/<id>.md` is HOW only and never carries spec the ticket lacks; the ticket wins on any disagreement (issue #53). To change spec: edit the ticket → docs PR/MR → merge → `publish-tickets.mjs --sync` (issue re-published from the ticket) → then execute. Never patch spec into a plan, into code, or by hand-editing an issue body.
- Ticket files are the issue-content source of truth. Issues are created only by `.claude/scripts/publish-tickets.mjs` (`[<id>]` title prefix = dedupe key); the issue body carries an auto-rendered dependency line (**Blocked by / Blocks** as issue `#numbers`, resolved from ticket `blocked_by`/`blocks` — the DAG is visible on the board, issue #52). To change an issue body, edit the ticket file and re-run with `--sync` (regenerates existing bodies from their ticket). Issue state (close) moves via the deliver step / `/verify-delivery`, never by hand mid-pipeline.
- Agents own the whole test pyramid: the Builder writes and runs unit + integration tests (and E2E where the ticket's acceptance calls for it); the Reviewer re-runs the full suite independently; the deliver step re-runs it on the merged default branch. The human tests exactly once per phase — the Gate 2 smoke test after that PRD's tasks are all done.
- Delivery is deterministic (`deliver-ticket.mjs`, issues #26/#50). **PR mode** (default when an origin remote + authenticated forge CLI exist): push the ticket branch, open a PR/MR carrying `Closes #N` + the plan, post the Reviewer's CLEAR verdict as a **comment** (the durable review trail), then merge **through the forge** (`gh pr merge` / `glab mr merge` — respects branch protection; a failing/pending required check escalates rather than force-landing), fast-forward the local default, close + verify the issue. No remote/forge → local `--no-ff` merge fallback. **GitLab with a 403 MR API + protected default branch** (issue #56) → **push-option MR**: opens the MR over SSH (`git push -o merge_request.*`, no MR API) with a single-line `Closes #N` description, posts the CLEAR verdict as an **issue comment** via the working Issues API, and stops for a human web-merge; a resume run detects the landed merge and closes/verifies via the Issues API. Mode is auto-detected (a cheap MR-API probe), overridable with `--delivery pr|direct|pushmr|auto`. The MR/PR body is the repo's own `.gitlab`/`.github` template, filled by the deliver agent from the ticket + diff + verdict + this CLAUDE.md's non-negotiables (the **Constraint check** section), not a hardcoded stub (issue #58). The deliver agent only stages the verdict + composed body under the ephemeral (git-ignored) `.claude/tmp/` and runs the one command; it never merges, pushes, opens PRs, or writes the tracker itself (that surface is blocked — issue #30). (`docs/plans/*.md` is git-ignored — the Architect's plan only needs to exist for the DoD, not be committed.)
