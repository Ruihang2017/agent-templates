# Pattern: Three-Agent Architect–Builder–Reviewer

| Field | Value |
|---|---|
| **Pattern name** | `three-agent-architect-builder-reviewer` |
| **Status** | `trialed` — signed off as the team standard 2026-07-17; promotes to `adopted` after its first real-ticket run (CLAUDE.md promotion rule) |
| **As-of date** | 2026-08-04 (every role cut one effort level — Architect `high`, Builder `medium`, Reviewer `high`, Triage `high`; §7) |
| **Expiry trigger** | First successor release to any listed model, or 2027-02-04 (+6 months), whichever comes first |
| **Sign-off** | Horace Hou (repo maintainer), 2026-07-17 |

One ticket flows through three agents in sequence: **Architect** plans → **Builder** implements → **Reviewer** (fresh context, different model tier) clears or bounces. No agent judges its own work.

## 1. When to use / when not to use

**Use when:**
- Ticket-scoped production changes where a bad merge is expensive: shared services, security-sensitive paths, concurrency-heavy code.
- The ticket is large enough to amortize three agent runs (rule of thumb: ≥ half a day of human-equivalent work).
- The team priority is predictable, reviewable delivery over token cost and latency — an explicit policy of this pattern.

**Do not use when:**
- Trivial or mechanical changes (typo fixes, config bumps, codemod output) — pipeline overhead dominates the value.
- Throwaway spikes and prototypes — a plan plus an independent review of disposable code adds nothing.
- Live pair-programming where a human already reviews every step in real time.

*(Scope guidance is design-derived, not a benchmark claim.)*

## 2. Agent roles & boundaries

| Agent | Does | Never does |
|---|---|---|
| **Architect** (Planner) | Reads the ticket and the codebase; produces the implementation plan. Exploration/tool-call heavy. | Writes production code. |
| **Builder** (Coder) | Implements against the Architect's plan; runs tests; iterates until passing. | Acts as the final judge of its own work; merges without Reviewer clearance. |
| **Reviewer** | Runs in a **fresh context** (never the Builder's session); reviews the Builder's output against the ticket and the plan, focusing on edge cases, concurrency, and security-sensitive paths. Clears the work or bounces it back to the Builder with findings. | Continues the Builder's session; fixes code itself. |

| **Triage** (nightly sweep only) | Classifies open tracker issues — fixable / invalid / needs-human — and synthesizes a cold-startable ticket file from each fixable one. | Fixes code; writes to the tracker (the report step owns all tracker writes). |
| **Delivery / cleanup** (executors, not judges) | Run one deterministic command each and relay its JSON. Delivery also composes the PR/MR body from artifacts it is handed. | Merge, push, open a PR/MR or close an issue directly; write or summarise a verdict; decide which branches may be deleted. |

### Why delivery is a stage and not a judgement

Delivery makes no judgement. It exists because of a **mechanical** constraint: a workflow script has no filesystem and no exec, so an agent is the only actor inside a running workflow that can invoke a command, and the orchestrator is unreachable from inside a run. That is the same reason the Codex sibling keeps its own delivery actuator — there, the primary thread is sandboxed read-only.

It is held to the narrowest remit the constraint allows:

- **It never writes or summarises a verdict.** The Reviewer authors its own record at `.claude/tmp/<id>-verdict.md`; delivery *verifies* the file exists and is non-empty and stops if it does not. This is the whole fix for the defect where a re-typed approval was blocked by a safety classifier three times, stranding CLEAR tickets (catalog issues #201, #208).
- **It never decides what may be deleted.** `cleanup-run.mjs` holds that rule. "Delete only the delivered ones" as prose is one summarisation away from deleting the only copy of work a human still has to look at.
- **It is given the facts it cannot see.** Bounce count, declared deviations, the Builder's summary — supplied explicitly, because a PR body that reads complete while being partly invented is worse than one that admits a gap (issue #193).

**The manual path exists too.** `/deliver-ticket <id>` runs the same procedure in your own session, after a `/review-ticket` CLEAR. Before it existed, `/review-ticket` ended at the verdict and an operator had to run the delivery script by hand, outside anything the pattern described. The main-session write guard carves out `.claude/tmp/` for exactly that, and nothing else.


### A verdict is a returned value, never a composed one

Two field reports, a day apart, are the same defect reached from opposite ends: the review stage ceasing to be independent (catalog issues #217, #218).

- **It must come back from a Reviewer-role subagent call.** A verdict the orchestration composed is not a verdict, however plausible it reads — and when a Reviewer died on a transport error, one was composed and handed to delivery. Every stage call is now wrapped so a rejection becomes a *stage failure* rather than an exception the run escapes through, and the deterministic retry-then-escalate path handles it. `delivered: 0` is an acceptable outcome; a fabricated CLEAR is not.
- **The Reviewer may not write, by any means.** Its tools include Bash because it must *run* the tests, so the role that may not write holds the one tool that can — and one used a heredoc to overwrite a production file, then reported that it had not. The guard now covers Bash for write-forbidden roles, and, independently of any pattern-matching, delivery refuses a branch whose head is not the commit the Builder finished on. The second check asks the Reviewer nothing.

The false report is the worse half. A Reviewer that misdescribes its own actions is not a Reviewer: the single property the role exists to supply is an accurate independent account, and that is exactly what failed.

The Reviewer is **deliberately a different model tier from the Builder** so the two do not share blind spots. This is a hard requirement of the pattern, not a cost knob.

Read that requirement precisely: it asks for a **different** model, not a **stronger** one. The mechanism is independence — two models fail differently, so one catches what the other misses — and it is satisfied in either direction. Since 2026-07-29 the Reviewer runs a *lower* tier than the Builder (Sonnet 5 judging Opus 5, §3), which keeps the independence the requirement is about while spending capability at the gate. What would break the requirement is collapsing the two onto the same model, in either direction (§4, tier collapse).

**Testing policy `[team-policy]` (2026-07-17):** the agents own the whole test pyramid. The Builder writes and runs unit + integration tests (and E2E tests where the ticket's acceptance calls for them); the Reviewer independently re-runs the full suite; the deliver step re-runs it on the merged default branch. Tests run manually or wired into the pipeline as fits the project. The human tests exactly once — the Gate 2 smoke test after the PRD's tasks are all done.

Related in-house variant: fx-eye-tracking's `planner` / `generator` / `evaluator` harness — same independence principle, heavier machinery (spec decomposition, file-scope parallelism, sprint contracts, tracker governance). That harness runs a whole project; this pattern runs one ticket.

## 5. Upstream / downstream integration

**Upstream (work intake)** — assumes the standard docs layout (exemplar: fx-eye-tracking):

- `docs/PRD.md` (master PRD) → `docs/prd/<module>/README.md` (sub-PRD) → `docs/prd/<module>/tickets/*.md` (one file per ticket; each ticket is a future issue body).
- **Later phases split the document, never the tree** (issue #112). Work added after a Gate 2 gets its own PRD — `docs/PRD-02-<name>.md`, passed to `/breakdown-prd <path>` — decomposed into the **same `docs/prd/`**. One root is not a convention but a constraint: `dag-scan.mjs`, `dag-report.mjs` and `/start-all` each take exactly one, and a cross-phase `blocked_by` resolves only inside one graph (a dangling ref is a hard failure by design). A parallel `docs/prd2/` would forfeit the single global DAG of issue #71 for nothing. In append mode `prd-phase.mjs context` supplies the next module prefix, the ticket ids already in use, and the existing-file list as **data**, and `prd-phase.mjs check` then enforces against git that pre-existing files under `docs/prd/` were only **added to** — never modified or deleted, because a delivered ticket is the record of what was built and `/start-all` cannot re-run it anyway. `--redo` is the explicit escape hatch for a pre-Gate-1 decomposition that was simply wrong. Running the new phase is just `/start-all` again: the earlier phases' issues are closed and filter out.
- The **ticket file is the Architect's input**; the Architect also reads the linked sub-PRD and any `docs/adr/` entries touching the affected area.
- The Architect's plan lands at `docs/plans/<ticket-id>.md`. A hard-to-reverse choice made while planning becomes a new ADR, not a paragraph buried in the plan.

**Downstream (deliverables):**

- Builder → an implementation on the ticket branch: code + passing tests, plus a deviations note where it departed from the plan.
- Reviewer → a verdict: **CLEAR** or **BOUNCE** (numbered findings: `file:line`, failure scenario, severity), **plus a review record it writes itself** to `.claude/tmp/<id>-verdict.md` — the acceptance rows it checked, the commands it ran with their real output, and what it could not verify. Nothing downstream re-types it: the delivery stage verifies the file is non-empty and points `deliver-ticket.mjs` at it. A missing or empty record **stops delivery** rather than being filled in by someone else (issues #201, #208). In an isolated worktree the Reviewer resolves the main repo root, so the record outlives the worktree. Findings go back to the Builder.
- Deliver step (deterministic, `deliver-ticket.mjs`) → the durable artifacts on the forge: the ticket branch pushed, a **PR/MR** carrying `Closes #N` + the plan, the Reviewer's **CLEAR verdict posted as a comment**, the PR/MR **merged through the forge** (branch protection respected), and the tracker issue closed-and-verified. No remote/forge → local `--no-ff` merge fallback; GitLab with a 403 MR API + protected default branch → `pushmr` (push-option MR over SSH, verdict as an issue comment, human web-merge) — issue #56. The MR/PR body is filled from the repo's own `.gitlab`/`.github` template (the delivery stage fills Type/Changes/Constraint-check/Evidence from the ticket, the diff, the Reviewer's own record and CLAUDE.md; `--body-file` → template skeleton → hardcoded fallback), not a fixed 3-section stub — issue #58. Bounce count, declared deviations and the Builder's summary are **supplied** to it rather than inferred, and any section it cannot fill from an artifact must say so plainly — issue #193.
- Net output: merged PR/MR with the review trail attached, updated docs/ADRs, closed ticket. Merge requires a CLEAR verdict.
- **Feedback channel (upstream):** pattern-level problems observed while running the pipeline — a role boundary that misfits, a stale model/effort pin, an orchestration bug — are filed as issues against the pattern catalog (`Ruihang2017/agent-templates`, issue templates provided); the catalog self-hosts the nightly sweep and triages them. Project-level bugs stay in the project's own tracker.
- **Identity and attribution on the forge (issue #137).** Every GitLab operation goes through **`glab`** and every GitHub one through **`gh`** — one authenticated surface, no raw API calls, which is what `settings.json`'s allow rules are written against. The CLI is authenticated by the **human**, with their own Personal Access Token (GitLab: the **`api`** scope alone suffices), installed via `glab auth login --stdin`; **the token is never given to an agent**, never an argument, never in a file the pipeline reads. Consequence to be explicit about: the pipeline acts **as that person**, so the forge shows a human as author and merger of machine-written code. `deliver-ticket.mjs` therefore prepends a rendered-visible banner to **every** MR/PR body — on all three body paths, so it cannot go missing on whichever one a repo happens to take — stating that the change was written and merged by AI, that an independent reviewer cleared it, and that the account shown is the token's owner rather than the code's author. Setup, scopes, and the 365-day expiry (which breaks the nightly sweep silently) are in [scaffold/INSTALL.md](scaffold/INSTALL.md#tracker-cli--token-setup).
- **Integration-branch fallback for a protected default branch (issue #139, opt-in).** Declare an `Integration branch:` line in CLAUDE.md and, in **autonomous** mode only, a merge the default branch refuses *because it is protected* is retargeted there (`ai-staging` by convention) rather than stalling every ticket. Three properties make it safe rather than a protection bypass: it fires **only** on a protection/permission refusal — an unmet gate still escalates, and the classifier fails closed on anything unrecognised; it is a different **target**, never a force-push or admin merge; and it is **outside the Definition of Done** — `dodPassed` stays false, the outcome is reported as the distinct `delivered-to-integration`, and both start commands must say plainly that those tickets are *not* on the default branch. The issue *is* closed, so a re-run does not rebuild work already on the branch, with a close comment naming where it went. At the end of a run one **handoff MR is opened and never merged** (`deliver-ticket.mjs --open-integration-mr`) — landing accumulated work on a protected branch is a human decision, which is the whole reason the branch was protected.
- **Publish without starting** (`/publish-tickets <module>`): creates the tracker issues and stops. It authorizes issue creation but is *not* Gate 1 sign-off to build — useful for populating the board before work begins, and the single place ticket → issue → Asana subtask happens (`/start-milestone` and `/start-all` run the same script).
- **Optional Asana mirror** (`integrations/asana/`, issue #126): when a repo has run `/connect-asana`, the pipeline mirrors itself into Asana at three points — module + ticket subtasks created right after issues are published (`/publish-tickets`, `/start-milestone`, `/start-all`); a ticket's subtask completed by `deliver-ticket.mjs` right after its issue closes, under the **same landed-merge precondition** as the tracker close; and drift reported by `/verify-delivery`. It sits **outside both human gates and outside the Definition of Done** — deliberately. `dodPassed` gates on `issueClosed` and never on Asana, because an expired token must not fail a ticket that shipped; the E2E asserts `dodPassed` is bit-identical with Asana healthy and with Asana returning 500. The paired obligation: every call site relays Asana `errors` into its report, since a mirror that silently stops mirroring is the §4 "Silent delivery drop" failure wearing a different hat. Direction is one-way — editing a subtask in Asana changes nothing; the ticket stays the source of truth (issue #53).
- Delivery is **verified, not assumed**: after every merge, `/verify-delivery <ticket>` checks the Definition of Done — plan on disk · **the forge's own checks green before the merge** (issue #205; a red or still-pending check refuses the merge rather than escalating after it) · tests green, **evaluated rather than assumed** — a run with no test command refuses to start, and `--no-tests` records a waiver instead of a pass · **CLEAR verdict attached to the PR/MR as a comment** · MR/PR merged into the default branch · tracker issue closed · writeback done. Added 2026-07-17 after the fx-eye-tracking silent-delivery-drop observation (§4); the verdict-attached item became mechanically real with PR-mode delivery (§4, issue #50).

**Human gates (target operating model):**

- **Gate 1 — upstream sign-off = the start signal:** once the module's sub-PRD and all its tickets are generated (from a bare PRD: `/breakdown-prd` generates them for review; format: the catalog's `templates/ticket.template.md`), a human types **`/start-milestone <module>`**. That one action is the sign-off. `/breakdown-prd` also writes **`docs/prd/dag.html`** (`dag-report.mjs`) so the reviewer can see the *execution shape* of the decomposition before signing it, not just the ticket list: **one flowchart of every ticket in the PRD**, colored by module, with the **recommended `concurrency`** to pass to `/start-all` derived from the ticket DAG rather than guessed. A module the page flags **fully serial** is a file-scope decomposition problem, and Gate 1 is the last cheap moment to fix it. The page renders two schedules over that one graph — *as the runner executes* (module barriers respected, which is what `/start-all` does today) and *globally scheduled* (only `blocked_by` gates) — and states the rounds lost to the barrier. The runner cannot execute the global schedule; that number is there to **price** the barrier, not to promise a speed-up (§4). The session then publishes every ticket as a tracker issue (`.claude/scripts/publish-tickets.mjs` — deterministic and idempotent, `[<id>]` title prefix as the dedupe key; agents never hand-create issues) and launches the milestone runner.
- **Gate 2 — smoke test:** a human smoke-tests the delivered work at the end of the ticket batch / milestone. **Per phase, not once per project** (issue #112): a project that adds a PRD phase after Gate 2 runs both gates again over the new document. The two-gate model bounds a *delivery*, it does not bound the project's lifetime.
- **The resume filter must report itself.** Closed-issue filtering is what makes re-runs — after a crash, a supervised pause, or an appended phase — safe, but a filter that drops work silently is indistinguishable from work that ran. `publish-tickets.mjs` returns each ticket's issue `state` in its summary, and `/start-all` relays what it skipped. A ticket whose text no longer matches its **closed** issue comes back as `drift`: either it was edited after delivery (a human decides whether to re-run it) or the issue predates a body-format change (`--sync` fixes that one). Either way it escalates; the scheduler never resolves it silently (issue #112).
- **Between the gates the pipeline runs autonomously** — `.claude/workflows/run-milestone.js` for a single module (`/start-milestone`, nightly sweep), `.claude/workflows/start-all.js` for the whole PRD. Per ticket both do: plan → build → review → on CLEAR, deliver = open PR/MR + verdict comment + forge-merge + close issue, with no per-ticket human approval. Stage order, reviewer freshness, the bounce cap, and no-merge-without-CLEAR are enforced **in code**, not prose — prose-only orchestration is a recorded failure mode (§4).
- **`/start-all` schedules from one flat DAG, and that DAG is live** (issue #71). It is not a sequence of `run-milestone` calls: every ticket in the PRD is gated only by `blocked_by`, so independent modules overlap. Every `rescanEvery` settled tickets — and always once more before finishing — it re-reads `docs/prd` through an agent, so **a ticket added while the run is in flight is published, scheduled, executed, and re-rendered into `dag.html`**. Workflow scripts cannot touch the filesystem, so that agent hop is the mechanism, not a convenience. What the scheduler *cannot* honor (a dependency added to an already-dispatched ticket, a cycle introduced mid-run, a failed reload, a hit runaway guard) is reported in `escalations` rather than silently applied — see §4.
- **Exception path (the only other way a human appears):** 2 bounce cycles without convergence, a failed build, or an unrepairable delivery item escalates to a human; the runner is fail-fast by default because later tickets may depend on earlier ones.
- **On-ramp:** a project newly adopting the pattern starts in `supervised` mode: the runner takes one ticket to a CLEAR verdict, **opens a PR/MR** (plan + verdict comment) and **stops the run** for the human to review + merge (later tickets may depend on the merged result). Re-run `/start-milestone` to continue — tickets whose issues are already closed are filtered out before the run, which also makes crash recovery mechanical. Switch to `autonomous` once the pattern holds. The mode is declared in the target repo's CLAUDE.md (see `scaffold/claude-md-snippet.md`).

**Orchestration mechanics:** a single ticket can still be run by hand with the stage commands; a milestone runs through the deterministic workflow. `ultracode` is not needed in target repos — typing `/start-milestone` is the explicit orchestration request (its instructions call the Workflow tool). Note that `ultracode` is a Claude Code **session setting** (`xhigh` effort + automatic workflow orchestration), not a model effort level — the pattern's pinned per-role efforts are unaffected by it. `[official]` — workflows + model-config docs, verified 2026-07-17 (record in `scaffold/INSTALL.md`).

**Whole-PRD driver (`/start-all`):** one sign-off runs every ticket in the PRD, scheduled from the flat `blocked_by` DAG (`dag-scan.mjs`; dangling refs and cycles are hard errors). Since 2026-07-27 it is **its own scheduler, not a sequence of `run-milestone` calls** (issue #71) — independent modules overlap instead of queueing. Failure policy (maintainer decisions, catalog issue #20, now applied per ticket rather than per module): a failed ticket cascades to its dependents; independent DAG branches continue in `autonomous`; anything short of a CLEAR stops everything in `supervised`; re-runs resume via closed-issue filtering (everything already delivered arrives filtered → `already-complete`). No cost ceiling by explicit `[team-policy]`. **`/start-milestone` is deliberately kept** for one module at a time — a different risk posture (module-boundary checkpoints during a fresh adoption, or uneven confidence across modules), not a redundant entry point.

**Parallel lanes (`concurrency`, opt-in):** `run-milestone`/`start-all` take a `concurrency` arg (default **1 = fully sequential, unchanged**). `>1` (autonomous only — supervised is forced to 1) runs independent tickets WITHIN a module as **parallel lanes**, DAG-scheduled from ticket `blockedBy`: each lane's builder + reviewer run in **isolated git worktrees** (the reviewer detached-checkouts the builder's commit — validated: a committed branch persists in the shared `.git` after worktree cleanup, and disjoint file-scopes make concurrent worktree builds + serialized merges clean), the architect writes the plan on the main tree and its **content is passed to the isolated builder** (a worktree can't see the gitignored plan), and **deliver is serialized** (merges to the default branch never overlap; a hidden file-scope overlap surfaces as a merge conflict → abort → escalate). Real parallelism is bounded by the DAG shape and the harness's `min(16, cores−2)` concurrent-agent cap, and it multiplies token spend — so it is opt-in per run. Under **`/start-all`** lanes are drawn from the whole PRD, so independent modules overlap (issue #71); under **`/start-milestone`** they are intra-module by definition, which is what the module barrier line in `dag.html` prices.

**Nightly issue sweep (unattended variant):** `claude -p "/nightly-issues"` on an OS schedule (Windows Task Scheduler etc.) while the machine is on. Flow: collect open issues → **Triage** (read-only; synthesizes tickets under `docs/prd/99-nightly/` for fixable ones) → **run-milestone** (autonomous, `continueOnFailure` — issues are independent) → one **report** step does all tracker writes: per-issue outcome comments, labels (`triage:invalid` / `nightly:escalated` / `needs-human`), closes delivered issues, and a `Nightly report YYYY-MM-DD` issue. The morning email is the tracker's own notification stream (watch the repo) — no SMTP to configure. Cost cap: `maxIssues` per night (default 5). Hand-written issues follow the catalog's universal tracker templates (`templates/tracker/`, installed to `.github/` / `.gitlab/`) so triage can convert them mechanically. Headless flags, permissions, and scheduling: `scaffold/INSTALL.md` § Nightly sweep.

**Re-adopting removes retired files.** `scaffold/pattern.json` lists files the pattern used to install and no longer does; `adopt` deletes each one it finds and says why. Copying new files in was never enough on its own — a withdrawn file would sit in the target beside its replacement, still loadable.
